# P05 API permissions and account isolation review

Prepared for Gerard on 2026-11-10. Review baseline: actual main `fdc7b6c11a8be94c72aa137773de4af8582d9640`, tree `fbbe9192fccd0e4dfd50724c2e13ba193fa2d0c9`, including merged P04. Executor: backend/security engineer. **D1–D8 engineering approved by the owner on 2026-11-10. Existing-key cutover and all other holds remain.** The baseline findings below are the pre-build investigation, not a claim about the engineering candidate.

API permissions currently do not restrict operations. Existing document queries do restrict access to the creating key, but this is not durable customer ownership. A second problem makes a simple scope check insufficient: deed metadata discloses a bearer confirmation link that can approve or reject the document. Administrator key management also accepts a revoked administrator access token.

The recommended work is a bounded permissions repair, a separate administrator-session repair, and a P08 ownership design. Do not replace key ownership with an organization filter during P05, and do not activate stricter v1 behavior until the owner approves the existing-key transition.

## Findings and consequences

|---|---|---|

Authenticated create/read/list/PDF/calculator handlers depend only on authentication (`:491`, `:654`, `:691`, `:744`, `:841`). Synthetic keys with read-only, create-only, empty, NULL and unknown scopes all created, listed and calculated successfully. A create-only key also read metadata and a completed PDF. | A restricted key is not restricted. Empty and unknown scopes are not safe defaults today. |
| Metadata carries an action capability | The shared create/replay/retrieve response includes the confirmation token at `backend/routers/api_v1/router.py:455`. The token lookup is independent of API-key authentication (`backend/routers/api_confirm.py:75`, `:101`). Synthetic metadata retrieval supplied a link that previewed and approved with no API key. | Calling metadata access read-only would be misleading even after adding `deed:read` checks. The link can also retrieve completed PDF bytes and the approval artifact. |

This is not an unauthenticated bypass and does not mean ordinary API keys are admin tokens. A separate repair needs approval. |

| Replacing a key strands its document access | `api_deeds.api_key_id` is the owner reference (`backend/database.py:607`), including the idempotency namespace (`:626`). | Test isolation is key isolation, not a durable document environment | `api_deeds` has no environment/class field (`backend/database.py:603`). The current key's `is_test` controls the watermark seam (`backend/routers/api_v1/router.py:551`). A test key could not read another live key's document, and vice versa. | Once P08 shares documents across successor keys, ownership alone will no longer separate test and live. The administrator refresh-token issuer does not include email/role (`backend/auth.py:75`), so the missing token-type check alone is **not** reported as a demonstrated refresh-token-to-admin exploit. The revoked administrator access-token reproduction is the observed defect.

## Proposed operation permissions

Permissions and ownership answer different questions. A permission allows an operation; an ownership check still restricts which record it can affect. No permission below implies another, and none grants cross-key or cross-customer access.

| Operation | Proposed permission | Boundary |
|---|---|---|
| POST `/api/v1/deeds`, including idempotent replay | `deed:create` | Current creating-key namespace and generation holds stay in place. |
| GET `/api/v1/deeds` and `/api/v1/deeds/{id}` | `deed:read` | Metadata only; do not disclose a handoff token without the separate permission below. |
| GET `/api/v1/deeds/{id}/pdf` | `deed:pdf` | Exact current owner key; completed stored bytes only. |
| Include `urls.confirmation` in create/replay/retrieve | `deed:handoff` | Without it, return the already-nullable field as null. Do not mint a second token or alter an existing approval. |
| POST `/api/v1/transfer-tax/calculate` | `tax:calculate` | Permission only; no tax-policy/profile/legal change. |
| Future partner-authenticated evidence export | Reserve `deed:evidence` | No such v1 route exists. Delivery belongs with P06/P12; reserving a name does not advertise an endpoint. |
| Future partner-authenticated usage retrieval | Reserve `usage:read` | No partner v1 route exists. Existing `/usage/*` routes are admin-guarded billing surfaces, not a partner usage API (`backend/phase23_billing/router_usage.py:12`). Do not expose or repurpose them. |
| GET `/api/v1/verify/{document_id}` and public specification | No API-key scope | Keep public verification minimal and independently rate limited. |
| Existing `/confirm/{token}*` surface | Existing bearer-link policy | Not an API-key scope. Scope checks control disclosure of the link, not the authority of a link already disclosed. |
| Existing `/try/deed` internal creation | Explicit authorized create and handoff policy | It directly calls real authentication and `create_deed` (`backend/routers/try_demo.py:281`, `:310`). A FastAPI-only dependency wrapper must not leave this internal path outside the shared authorization check. No demo credential changes here. |

Centralize this in one operation registry and one authorizer used by both HTTP and internal calls. Missing permission returns structured 403 before rendering or document persistence. An authorized caller requesting another key's record still receives 404. Unknown operations fail closed; unknown requested scope names are refused at issuance. Scope checks must not authenticate or increment rate counters twice. Scope denial must not trigger a lifecycle sweep or log bearer values.

A read-only key would have `deed:read`, with optional separate PDF/evidence permissions. A creation-and-handoff integration would need `deed:create`, `deed:read`, `deed:handoff`, `deed:pdf`, and `tax:calculate` only if it uses the calculator. This is an explicit selected template, not a database default or automatic grant. Creating a draft does not record a human approval.

Prove successor-key access only after explicit owner/environment mapping; preserve historical document IDs, artifact bytes, approval evidence and idempotency meaning. Production migration is separate and held.

## Review evidence and limits

Runtime reproductions use actual router handlers, real API-key bcrypt validation and SQL predicates against the marked disposable database at loopback port 55439. No authorization dependency is replaced. Only PDF rendering is stubbed with synthetic bytes, so these are authorization/ownership proofs, not rendering, watermark-layout, full-application-browser or production claims. The minimal test app mounts the same v1, confirmation and key-management routers; the supplemental admin test also uses the real request-scoped connection mechanism.

The [review evidence receipt](platform_p05_review_2026-11-10.json) records **27 completed authorization/ownership observations plus one successful administrator-session reproduction**. Several observations deliberately confirm a defect, not a security guarantee. An initial local database launcher used the wrong port and the guard refused to connect; a private network fence initially blocked Windows asyncio's loopback socketpair; a private hold check expected handler-level 409 instead of the existing create-model 422; and an interrupted local PostgreSQL process forced recovery and stopped a later run. The owned server was restarted in an observed foreground session and the final 27-observation run completed. These are review-tool/setup corrections, not application repairs. Failed attempts are retained; none is counted as a completed pass.

No production caller inventory was read. No real customer count, active integration compatibility, legacy ownership mapping or historical exposure is inferred from synthetic results. Passing the tested key-isolation cases does not clear application sharing, tenant migration, token compromise, administrator compromise or a complete external security assessment.
