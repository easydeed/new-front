# P04 Contact retention and approval evidence decisions

Prepared for Gerard on 2026-11-10. Investigation baseline: main `ca56c8fe184dbff2437f04dc50f1fcefdac6fea8`, after reviews 304–306. **D1–D7 engineering approved by the owner on 2026-11-10**, explicitly retaining optional email in one purgeable location for compatibility. Production cleanup, deployment changes, customer-facing publication and P03 activation remain held. The findings below describe the investigation baseline, not a claim that the engineering candidate has already passed its gates.

The defect is real: optional approver email enters both a purgeable column and the saved request. The purge clears only the column, while approval hashes the saved request. Correcting new writes is straightforward; deleting historical copies without misrepresenting the old hash requires a separate, explicit transition.

P03's instrument holds, disabled county profiles, unmounted v2 router, legal wording/applicability hold and broader v1 tax cutover hold remain unchanged. P04 does not activate tax profiles, approve declarations or retroactively approve previews.

For D4, the tradeoff cannot be hidden: once an email-containing historical hash input is redacted, that original digest cannot be recomputed from the redacted JSON. A transition record may reference the original digest and bind a new contact-free snapshot, but it is not a new human approval and cannot make the old digest validate different bytes. Retaining an untouched hidden copy forever would defeat contact deletion. Hashes are not, by themselves, proof that personal data has been anonymized.

## Engineering sequence and release boundaries

1. **Evidence and new writes.** Specify one canonical serialization, explicit evidence scheme/version, and a separate evidence digest. Preserve original legal strings; do not trim, infer or recalculate instructions. New saved request snapshots exclude only the dedicated optional contact field. Contact stays in its governed location if D1 is approved. Capture actual approval metadata atomically with promotion of the same PDF bytes; bind the existing declaration text/version as presented without upgrading it into identity, reading, notarization or legal-sufficiency proof. Do not backfill a missing historical display or acceptance as if witnessed.
2. **Lifecycle and status.** Reuse the shared retention decision, UTC event clock and existing coordinated job. Detect governed copies by their actual location/content and evidence version, not only an old purge stamp. Distinguish eligible overdue, held, unknown-clock and legacy-transition-required records. Count remnants in JSON even when the contact column is null. A new implementation must not make the request-triggered sweep start redacting unapproved legacy rows on deployment.
3. **Historical tooling preparation.** Prepare aggregate dry-run inventory and an explicit owner-operated, version-aware transition. Separate completed legacy approvals, pending previews, rejected/expired records, already-stamped JSON leftovers and exceptional/held rows. Preserve idempotency and the existing exact demo markers. Verify originals before any proposed transition; record discrepancies without “repairing” old hashes. Apply only after count review and separate batch authorization.
4. **Operational and policy closure.** Prove idle-period execution in an approved disposable environment, then hand the production job and backup/log verification to the owner. A restored backup stays isolated until approved due purges and hold reconciliation are complete. Customer copy is reviewed separately. New-write engineering can be reviewed independently, but P04 must not be called complete while legacy remnants or operational coverage remain unresolved.

Each implementation concern gets its own PR from actual main, full verification and main receipt. No automatic deployment, credential work, production cleanup, whole-row deletion, artifact rewrite or additional ticket is included in the investigation approval.
